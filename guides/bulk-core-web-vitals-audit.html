How to run bulk Lighthouse and Core Web Vitals audits for many websites

Who this is for: web and SEO agencies auditing client or prospect sites, developers checking which templates are slow, and anyone who wants a weekly alert when a deploy makes pages slower.

Tool used: Lighthouse & Core Web Vitals Bulk Auditor (Apify Store, pay per page audit). It runs the official lighthouse npm package (v13) in Google Chrome, the same engine as PageSpeed Insights and Chrome DevTools.

What you get per page and device

  • Performance, accessibility, best-practices and SEO scores (0-100), an overall score and an A-F performance grade
  • Lab Core Web Vitals: LCP, CLS and TBT (the lab stand-in for INP), plus FCP, Speed Index, TTI and TTFB, each rated good / needs-improvement / poor, and coreWebVitals.passesLab
  • topFixes: performance opportunities ranked by estimated time saved, then failing accessibility, SEO and best-practice checks, each with a plain-English fix and a docs link
  • Page weight by type, third-party share and the heaviest third parties
  • The LCP element and where its time goes
  • Optional full Lighthouse HTML report per page (htmlReportUrl)

Step 1: Build the URL list

Bare domains audit the homepage. Full URLs audit that page. To cover more than the homepage without listing pages by hand, set maxPagesPerDomain (1-10) and the Actor adds pages from the sitemap or homepage links, one per section.

Step 2: Run the audit

Open the Actor page, click Try for free, and use the form or this JSON:

{
  "urls": ["clientone.com.au", "https://www.clienttwo.com/pricing", "clientthree.co.uk"],
  "strategy": "both",
  "maxPagesPerDomain": 3,
  "saveHtmlReports": true,
  "maxFixes": 8,
  "reportTitle": "Website speed audit"
}
  • strategy: mobile (the default, and what PageSpeed Insights shows first), desktop or both.
  • Memory: the default is 4 GB, and the Actor runs one audit per 4 GB so parallel audits don't skew scores. Give the run more memory to finish big lists faster.

Step 3: Read the results

  • The Scores and Core Web Vitals view is the summary table. Sort by performance to find the slowest pages.
  • The Ranked fixes view lists what to fix first on each page, with links to each HTML report.
  • The key-value store has a run summary (OUTPUT), a printable REPORT_HTML and REPORT_CSV.

Google's published "good" thresholds for Core Web Vitals are LCP of 2.5 seconds or less, CLS of 0.1 or less and INP of 200 ms or less (web.dev/vitals). Lab runs can't measure INP, so TBT is reported in its place.

Step 4 (optional): Add real-user field data

Lab scores come from one simulated load. For the real-user data Google uses in Search (Chrome UX Report), add your own free PageSpeed Insights API key in pageSpeedApiKey. Those audits run through Google's API, add a fieldData block (LCP, INP and CLS at the 75th percentile with ratings and passesCoreWebVitals), and cost less because Google does the work. Get a key from the PageSpeed Insights API docs.

Step 5: Monitor scores every week

  1. Add "monitorName": "client-sites" and, optionally, "alertOnScoreDrop": 5 to the input.
  2. Save it as an Apify Task and attach a Schedule (for example every Monday at 6 am).
  3. From the second run on, each row has a monitor block with the change since the last run, regression: true|false and regressedCategories.

Scores move a few points between runs on any machine, so keep alertOnScoreDrop at 5 or more.

Automate it with Make or n8n

  • Make: Apify app Watch Actor Runs (fires when the scheduled run finishes), then Get Dataset Items, then a filter on monitor.regression = true, then Slack, email or Google Sheets. Apify's Make guide shows the modules.
  • n8n: the Apify node's On new Apify Event trigger (Succeeded) for this Actor, then Get Dataset Items, then an IF node on monitor.regression (Apify's n8n guide).
  • API:
curl -X POST "https://api.apify.com/v2/acts/ausbizstack~lighthouse-core-web-vitals-bulk-auditor/runs" \
  -H "Authorization: Bearer YOUR_APIFY_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"urls": ["clientone.com.au"], "strategy": "mobile", "monitorName": "client-sites"}'

Lighthouse audits take tens of seconds each, so for long lists start the run asynchronously like this and fetch the dataset when it finishes, rather than waiting on a synchronous call.

FAQ

Why is my score different from PageSpeed Insights? Both use Lighthouse with simulated mobile throttling, but each run varies a little with network and server response. Compare trends across runs, not single points.

Is it safe to audit an untrusted URL list? The audited page runs in a sandboxed headless Chrome whose requests go through a filtering proxy that refuses private, internal and cloud-metadata addresses.
